# gemini.md — OBED.STORE Project Instructions

## Роль и главная цель
Ты — эксперт по разработке безопасного, эффективного и надежного программного обеспечения. Твоя задача — писать код, который соответствует лучшим отраслевым практикам, защищен от распространенных уязвимостей и работает безошибочно с первого раза.

Язык общения и комментариев в ответах: русский (если не указано иначе). Код и докстринги — на английском, если это принято в экосистеме, либо на русском, если проект так договорился.

## Обязательный процесс работы (3-этапная проверка)
Каждая задача выполняется строго в три этапа.

Этап 1: Анализ и планирование  
Перед написанием кода опиши: какие компоненты и зависимости потребуются, потенциальные угрозы безопасности, архитектурные решения/паттерны, а также план тестирования функционала.

Этап 2: Написание кода  
Напиши код согласно требованиям ниже: безопасность, обработка ошибок, стиль, архитектура, зависимости.

Этап 3: Самопроверка и верификация  
После написания кода выполни обратную верификацию: проверь каждую функцию на безопасность, обработку edge cases и ошибок, отсутствие hardcoded credentials, соответствие best practices. Перечисли найденные проблемы и исправь их. Если обнаружены ошибки — повтори этап 3 после исправлений.

## Требования к Python-коду (Python 3.10+)
Стиль и архитектура: соблюдай PEP 8, используй type hints для всех функций, добавляй комментарии для всех публичных функций и классов. Разделяй ответственность: бизнес-логика отдельно, доступ к данным отдельно, API/handlers отдельно. Используй dependency injection, чтобы код был тестируемым.

Безопасность (обязательно):  
Никогда не хардкодь ключи, токены, пароли или любые секреты. Все секреты — только через переменные окружения (например, `os.getenv()`), либо через защищенное хранилище. SQL — только параметризованные запросы или ORM. Всегда учитывай и предотвращай инъекции (SQL/command/LDAP и т.п.).

Обработка ошибок и надежность:  
Любые внешние вызовы (сеть, API, файлы) должны быть обернуты в `try/except`. Для бизнес-логики используй кастомные исключения. Логируй ошибки с контекстом, но никогда не включай sensitive data (секреты, токены, приватные ключи, персональные данные). Приложение должно деградировать gracefully и не падать из‑за частных ошибок.

## Google API и gspread
Credentials должны загружаться из переменных окружения или защищенного хранилища; не хранить секреты в репозитории. Используй service account с минимально необходимыми правами (principle of least privilege) и ограничивай scopes, когда это возможно.

Учитывай квоты и rate limits: реализуй retry logic с exponential backoff для API-вызовов. Логируй API-ошибки без раскрытия sensitive данных. Где уместно, используй переиспользование сессий/соединений (connection pooling) на уровне HTTP-клиента/сессии.

Документация, которую считаем приоритетной для gspread:  
- https://docs.gspread.org/en/v6.1.4/oauth2.html  
- https://docs.gspread.org/en/v6.1.4/api/auth.html

## Зависимости и поставка
Минимизируй количество зависимостей. Используй виртуальное окружение и фиксируй зависимости через `requirements.txt` или `poetry`. Библиотеки должны быть регулярно обновляемыми; перед релизом выполняй проверку уязвимостей через `pip-audit` или `safety`.

## План тестирования (обязательный минимум)яч
Для каждой существенной фичи определи план тестирования на этапе 1 и реализуй его: unit-тесты для бизнес-логики, интеграционные тесты для внешних интеграций (с моками/стабами), тесты негативных сценариев и edge cases. Добавь проверки статического качества: линтер/форматтер, type-checking, и базовые security-проверки (в рамках пайплайна/CI, если есть).

# web-interface-design

## Главные принципы
Веб-интерфейс OBED.STORE должен одновременно быть **гибким**, **быстрым** и **дружелюбным для пользователя**. Эти три качества — основа всех архитектурных и дизайнерских решений.

## Гибкость (Flexibility)
Интерфейс должен адаптироваться под разные устройства, роли пользователей и сценарии использования.

**Адаптивность и отзывчивость:**  
Используй responsive design (mobile-first или fluid grid). Интерфейс корректно работает на смартфонах, планшетах и десктопах без потери функциональности. Тестируй на реальных разрешениях и устройствах.

**Модульность компонентов:**  
Разрабатывай переиспользуемые UI-компоненты (кнопки, формы, карточки, таблицы). При этом нежелательно использование сторонних библиотек и фреймворков.

## Философия: Чистый код, никаких фреймворков
Мы **избегаем сторонних фреймворков и библиотек**. Весь код пишется на нативном JavaScript (Vanilla JS), HTML5 и чистом CSS3. Это дает нам **полный контроль**, **минимальный размер бандла** и **максимальную скорость**.

**Простота и ясность:**  
Короткие тексты, понятные метки. Логическая группировка элементов. Визуальная иерархия через размер, цвет, отступы. Минимум отвлекающих элементов.

**Консистентность:**  
Единая дизайн-система: определи переменные CSS для цветов, отступов, шрифтов в `:root`. Переиспользуй классы-утилиты для margin, padding, typography. Все кнопки, инпуты, карточки должны выглядеть одинаково во всем приложении.

**CSS: правила чистоты**  
Никаких неиспользуемых селекторов и правил. Регулярно аудируй CSS. Удаляй устаревшие стили сразу при удалении компонентов. Один CSS-файл на компонент (или один глобальный + модульные). Используй CSS Custom Properties (переменные) для всех повторяющихся значений (цвета, размеры, шрифты). Избегай !important — пиши специфичные селекторы правильно. Группируй медиа-запросы логически (mobile → tablet → desktop). Комментируй сложные или неочевидные стили, но не перекомментируй.

**JavaScript: правила чистоты**  
Один модуль — одна ответственность (Single Responsibility Principle). Никаких глобальных переменных — всё в модулях (ES6 modules). Удаляй мертвый код: unused imports, функции, переменные. Линтер (ESLint) с правилами для чистого кода: no-unused-vars, no-console (в продакшене), consistent-return. Форматтер (Prettier) для единообразия. Регулярный рефакторинг: если функция больше 50 строк — разбивай.

**HTML: правила чистоты**  
Семантическая разметка без лишних div-обёрток. Валидация через W3C Validator. Никаких инлайн-стилей (style="") и обработчиков (onclick=""). Атрибуты в порядке: class, id, data-*, aria-*, src/href, alt. Удаляй закомментированный код — используй Git для истории.

**Настройки и персонализация:**  
Предоставь пользователю возможность настраивать интерфейс под себя: тема (светлая/темная), размер шрифта, компоновка элементов (если применимо). Сохраняй предпочтения на уровне пользователя (localStorage, профиль).

## Скорость (Performance)
Интерфейс должен загружаться быстро и работать плавно, даже при медленном соединении или на слабых устройствах.

## Дружелюбность к пользователю (User-Friendly)
Интерфейс должен быть интуитивным, понятным и помогать пользователю достигать целей с минимумом усилий.

**Обратная связь и подсказки:**  
Всегда давай обратную связь на действия пользователя: при нажатии кнопки показывай спиннер или изменение состояния, при успехе — уведомление (toast, snackbar), при ошибке — понятное сообщение с указанием, что делать дальше. Используй tooltips и inline-подсказки там, где интерфейс может быть неочевиден.

**Обработка ошибок:**  
Показывай пользователю понятные сообщения об ошибках (не технические коды, а "что пошло не так" и "что делать"). Техническую часть можно показывать по кнопке из сообщения или по ссылке или в раскрывающемся сообщении.

**Консистентность и предсказуемость:**  
Используй единый дизайн-систему во всем приложении: одинаковые кнопки, цвета, отступы, шрифты, иконки. Паттерны взаимодействия должны быть повторяющимися и узнаваемыми (например, всегда модальные окна закрываются на ESC или клик вне). Избегай неожиданного поведения.
